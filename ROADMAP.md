План-преемник [BUILD-PLAN.md](BUILD-PLAN.md) (MVP собран). Решения зафиксированы в интервью — не переспрашивать, выполнять как написано. Каждый шаг = одна итерация: открыть **новую сессию** в папке проекта и вставить промпт шага как есть. Шаги выполнять строго по порядку, каждый — отдельной веткой/PR поверх предыдущего.

**Контекст проекта:** локальное веб-приложение для живых партий D&D 2024 (доска на ТВ, консоль мастера, телефоны игроков), всё по-русски. После правок `shared/` обязателен `npm run build -w shared`.

## Шаг 2 — Серверный боевой движок + протокол

**Решения:** мгновенная резолюция без подтверждения мастера; урон применяется сервером автоматически (мастер может поправить руками); криты: 20 — автопопадание и двойные кости урона (бонус не удваивается), 1 — автопромах, у обеих сторон; спасброски МОНСТРОВ кидает мастер (физически или виртуально) через очередь; спасброски ИГРОКОВ — большая кнопка на телефоне (виртуально или вписать физический результат), мастер может вписать за игрока (фолбэк); концентрация — автоматический спас Телосложения (Сл 10 или половина урона, что выше) при каждом получении урона, при провале концентрация снимается с записью в лог; дальность по карте в v1 не проверяется; области — мультивыбор целей из видимых врагов, геометрию не считаем; ячейки монстров живут на токене сессии (два гоблина-мага тратят раздельно); долгий/короткий отдых переводится с REST на WS, чтобы доска видела.

**Промпт:**

> Сессия продолжает план из ROADMAP.md (шаг 2), решения подтверждены — список решений читай в ROADMAP.md, шаг 2. Построй серверный боевой движок VibeDND поверх оцифрованных заклинаний (шаг 1 смержен):
> 1. Протокол (`shared/src/protocol.ts`): новые ClientMsg — `castSpell { characterId|tokenId, spellId, slotLevel, targetTokenIds[] }`, `attackWith { attackerTokenId|characterId, attackName|weaponItemId, targetTokenId }`, `saveResult { requestId, value }` (вписанный физический результат) и `saveRoll { requestId }` (виртуальный бросок), `resolveSave { requestId, rolledValue? }` (мастер кидает/вписывает за монстра), `rest { characterId, kind }`. Новые ServerMsg — `combatEvent` (структурированное событие боя: фаза `cast` | `damage` | `save-request` | `death`, участники, попадания, урон, крит, тип эффекта для анимаций), `saveRequest` (кому кинуть, какая характеристика, Сл), обновлённый боевой лог. Свободный `rollDice` остаётся для нефритовых бросков.
> 2. Движок (`shared/src/rules.ts`): функции разрешения атаки (d20 + бонус vs `Monster.armorClass` / AC персонажа, криты 20/1), каста (проверка и трата ячейки `spellSlotsCurrent` — у персонажа и у токена монстра; заговоры без ячеек; upcast-урон), спасбросков (halfOnSuccess), урона. Всё детерминированно на сервере.
> 3. `server/src/ws.ts`: хендлеры новых сообщений; автоматическое применение урона к токену (clamp 0..maxHp, существующая синхронизация токен↔персонаж) + broadcast `combatEvent`; очередь спасбросков (состояние в сессии: requestId, кто кидает — DM за монстров / владелец за персонажа, вписать или кинуть); авто-спас концентрации при любом уроне; смерть токена (0 HP) — отдельное событие; `rest` через WS вместо REST-кнопок CharacterSheet (кнопки перевести на WS).
> 4. Сохранение: как сейчас — снапшот сессии в SQLite после каждой мутации (`db.saveSession`).
> Напиши серверный сценарий-проверку (`node`, не tsx): castSpell тратит ячейку, крит/промах, save-очередь, halfOnSuccess, концентрация слетает. UI в этом шаге не делаешь (шаги 3–4), но protocol.ts типизируй полностью. `npm run build -w shared`. Отдельная ветка + commit.

## Шаг 3 — Боевой UI игрока (телефон)

## Шаг 5 — Анимации боя на канвасе

**Решения:** рисовать в новом слое канваса `MapCanvas` (не DOM); доставка — `combatEvent` из шага 2, две фазы: фаза каста/атаки проигрывается **мгновенно** при получении события (задержка минимальна — это требование), фаза урона — когда сервер присылает damage-событие (после спасбросков); хореография целиком на клиенте: снаряд/луч летит ~0,5 с → вспышка попадания → цифра урона над токеном → полоска HP убывает; обычные атаки без спасбросков — одно событие, всё сразу; без библиотек анимации и без звука; оптимизация обязательна: существующий rAF-цикл канваса, жёсткий лимит частиц, эффект после завершения полностью удаляется из списка отрисовки; переключатель «анимации вкл/выкл» в настройках доски.

**Набор эффектов v1:** снаряд (стрела/болт — линия полёта), взмах (ближний бой — дуга у цели), заклинание по цвету школы (огонь оранжевый, холод голубой, молния жёлтый, некротика фиолетовый, остальное — золото), попадание (красная вспышка + цифра урона), крит (золотая вспышка, крупная цифра), промах (серый «мимо»), спасбросок (щит-символ у цели), лечение (зелёный), смерть (существующий ☠ + затухание токена).

**Промпт:**

> Сессия продолжает план из ROADMAP.md (шаг 5), решения и набор эффектов — в ROADMAP.md шаг 5. Сделай анимации боя VibeDND в `web/src/components/MapCanvas.tsx` (боевые события `combatEvent` уже приходят в стор из шагов 2–4):
> 1. Новый слой эффектов поверх токенов в существующей системе слоёв канваса (image → grid → tokens → **fx** → drawings → fog), в текущем rAF-цикле; эффекты живут в ref-списке, каждый имеет время жизни и по завершении удаляется.
> 2. Хореография по фазам события: cast-фаза — снаряд/взмах/луч от источника к цели(ям) ~0,5 с сразу по получению; damage-фаза — вспышка попадания, всплывающая цифра урона, затем анимированное убывание полоски HP; крит — золотая вспышка и крупная цифра; промах — серый «мимо»; спас — символ щита; лечение — зелёный; смерть — затухание токена к ☠.
> 3. Цвет заклинания по школе (`school` из данных события): evocation-fire оранжевый, холод голубой, молния жёлтый, necromancy фиолетовый, остальные школы — золото.
> 4. Жёсткий лимит одновременных эффектов и частиц (например ≤20 эффектов), деградация без падения FPS; никаких библиотек, никакого звука.
